# PRD: Cherry Studio 企业 AI 客户端 P0

## 0. 文档目的

本文档面向 Cherry Studio 产品、架构和开发拆解使用，定义 P0 阶段如何把 Cherry Studio 从偏个人配置型 AI 桌面客户端，改造成可接入企业 AI Infrastructure 的纯客户端入口。本文基于 `_bmad-output/brainstorming/brainstorming-session-2026-05-29-213953.md`，并将偏架构实现的细节沉淀到同目录 `addendum.md`。PRD 正文只定义产品边界、用户体验、功能需求、非功能要求、成功标准和开放问题；技术方案细节留给后续架构文档。

## 1. Vision

Cherry Studio 企业 AI 客户端 P0 的目标是让普通员工不再理解 Provider、Base URL、API Key、模型配置等个人工具概念，而是通过企业授权登录直接获得可用的企业 AI 能力。登录后，员工至少可以使用企业统一提供的模型、知识库和技能，以最低配置成本完成日常问答、知识检索和轻量工具调用。

P0 不把 Cherry Studio 改造成企业 AI 管理后台，也不在本地复制企业资源主数据。企业 AI Infrastructure 是模型、资源、权限、授权页和治理策略的唯一上游。Cherry Studio 只作为桌面客户端消费上游能力，负责登录入口、凭据保存、资源发现、轻量展示、调用入口和本地体验衔接。

首版策略是最小改造、尽快跑通闭环：新增或强化企业专用 Provider 接入语义，复用现有模型调用、知识库和技能入口，做一个轻量企业入口，而不是重做完整首页、首页 Agent、岗位能力包或专业模式。

## 2. Target User

### 2.1 Jobs To Be Done

- 作为普通员工，我希望打开 Cherry Studio 后通过企业账号登录，不需要找管理员要 API Key 或手动配置 Provider。
- 作为普通员工，我希望登录后默认有可用模型，可以直接问 AI。
- 作为普通员工，我希望能看到企业分配给我的知识库，并在对话或知识入口中使用它们。
- 作为普通员工，我希望能使用企业分配给我的技能，而不需要理解技能从哪里安装、如何配置。
- 作为企业 IT / AI 平台团队，我希望 Cherry Studio 只是企业 AI Infrastructure 的客户端消费端，权限、资源配置和授权逻辑继续在上游统一治理。
- 作为开发团队，我希望 P0 尽量复用现有 Provider、知识库、技能和 IPC / DataApi 边界，避免重做本地产品结构。

### 2.2 Non-Users (P0)

- 企业管理员：P0 不提供资源配置、权限配置、岗位能力包管理或可见性管理后台。
- 专业 AI / Agent 高级用户：P0 不实现专业模式切换、多 Provider 自由配置增强或高级 Agent 客户端能力。
- 后端平台开发者：P0 不在 Cherry Studio 内实现企业 AI Infrastructure 的服务端能力。

### 2.3 Key User Journeys

- **UJ-1. 普通员工首次登录后直接问 AI。**
  - **Persona + context:** 新员工第一次安装企业版 Cherry Studio，只知道公司提供 AI 工具，不知道 API Key 或模型供应商。
  - **Entry state:** Cherry Studio 已安装，未登录企业账号。
  - **Path:** 员工打开应用，看到轻量企业入口；点击企业登录；系统打开企业 AI Infrastructure 的授权页；授权完成后回到 Cherry Studio；应用显示已登录状态和默认可用模型。
  - **Climax:** 员工在聊天入口直接提问并得到企业模型回复，无需任何手动 Provider 配置。
  - **Resolution:** 员工保持企业登录态，后续打开应用可继续使用企业模型。
  - **Edge case:** 授权失败或取消时，员工回到未登录状态，并看到可重新登录的明确入口。

- **UJ-2. 普通员工使用企业知识库回答业务问题。**
  - **Persona + context:** 员工需要查询公司内部制度、产品资料或业务知识，但不知道知识库具体存在哪里。
  - **Entry state:** 员工已企业登录，上游已给该员工分配至少一个知识库。
  - **Path:** 员工进入现有知识库或对话相关入口；看到企业知识库列表；选择一个知识库；发起问题；系统使用远端知识库能力返回回答或检索结果。
  - **Climax:** 员工获得基于企业知识库的答案，并能识别该答案来自已授权的企业知识来源。
  - **Resolution:** 员工无需导入文件或复制知识库，本地只保留必要会话态、缓存态和偏好。
  - **Edge case:** 没有可见知识库时，界面解释“当前账号暂无可用企业知识库”，不引导员工本地创建企业资源副本。

- **UJ-3. 普通员工使用企业技能完成轻量任务。**
  - **Persona + context:** 员工需要调用企业预置技能完成文本处理、信息查询或流程前置任务。
  - **Entry state:** 员工已企业登录，上游已给该员工分配至少一个技能。
  - **Path:** 员工从现有技能入口或对话中的技能选择入口查看可用企业技能；选择技能；输入必要参数；Cherry Studio 调用上游能力完成执行；结果回到当前会话或技能结果区域。
  - **Climax:** 员工不安装、不配置技能，也能使用企业分配的技能完成任务。
  - **Resolution:** 技能权限、版本和可见性仍由上游控制。
  - **Edge case:** 技能被上游撤销或执行失败时，Cherry Studio 显示可理解错误并刷新可用资源状态。

- **UJ-4. 员工登录态失效后恢复使用。**
  - **Persona + context:** 员工长期使用后 token 过期，或上游撤销授权。
  - **Entry state:** Cherry Studio 本地存在旧登录态，但访问模型、知识库或技能时被上游拒绝。
  - **Path:** 系统检测授权失效；尝试客户端允许的刷新路径；刷新失败时清理不可用会话状态；提示员工重新企业登录。
  - **Climax:** 员工明确知道需要重新登录，而不是看到模型、知识库或技能的模糊失败。
  - **Resolution:** 重新登录后，Cherry Studio 重新拉取模型、知识库和技能资源。

## 3. Glossary

- **Cherry Studio 企业 AI 客户端** — 本 PRD 定义的 Cherry Studio P0 形态。它是企业 AI Infrastructure 的桌面客户端消费端，不承担服务端治理逻辑。
- **企业 AI Infrastructure** — 统一上游系统，负责 OAuth 授权页、身份、token、模型、知识库、技能、权限、资源治理和可见性配置。
- **企业 Provider** — Cherry Studio 中承接企业模型调用的内部接入实体。它对员工不暴露为 Provider 概念，用户界面表达为“企业 AI”或后续确定的企业能力名称。
- **企业登录态** — Cherry Studio 本地保存的、由企业 AI Infrastructure 授权产生的客户端认证状态，包括访问企业模型、知识库和技能所需的凭据或刷新材料。
- **远端资源** — 企业 AI Infrastructure 中的模型、知识库或技能。远端资源的主数据不归 Cherry Studio 所有。
- **资源元数据** — Cherry Studio 为展示和调用远端资源所需的最小描述信息，例如名称、类型、描述、可用状态、权限提示和调用入口。
- **远端知识库** — 企业 AI Infrastructure 分配给当前员工的知识库。P0 中 Cherry Studio 只消费它，不把它复制为本地主数据。
- **远端技能** — 企业 AI Infrastructure 分配给当前员工的技能。P0 中 Cherry Studio 只展示、选择和调用它，不负责技能治理。
- **远端可执行入口** — P0 对远端技能的限定形态，由企业 AI Infrastructure 提供元数据、输入 schema、调用接口和结果 schema。它不是本地 Agent 编排、MCP 工具注册、工作流编排或技能市场能力。
- **轻量企业入口** — P0 中用于登录、展示企业登录状态、暴露默认模型和资源入口的最小 UI。它不是完整混合首页，也不是首页 Agent。
- **普通员工** — P0 的主要用户。默认不理解或不需要接触 Provider、API Key、Base URL、权限配置和资源治理。
- **专业模式** — 面向高级用户的多 Provider、高级配置或更自由 Agent 能力入口。P0 不实现。
- **客户端纯边界** — Cherry Studio 在本项目中只做客户端行为，不新增企业服务端逻辑、权限治理后台或资源管理后台。
- **单企业账号策略** — P0 同一时间只支持一个活跃企业账号。切换企业账号需要清理上一企业账号的企业登录态、远端资源元数据缓存和企业偏好。
- **P0** — 本 PRD 定义的首版范围，只覆盖企业登录、企业 Provider、模型、知识库、技能和轻量入口。

## 4. Features

### 4.1 企业登录与企业 Provider 激活

**Description:** 普通员工从 Cherry Studio 中发起企业登录。企业 AI Infrastructure 提供 OAuth/授权页和服务端授权逻辑，Cherry Studio 只负责打开授权入口、接收回调、保存客户端登录态、激活企业 Provider，并在授权失效时引导重新登录。实现 UJ-1、UJ-4。

**Functional Requirements:**

#### FR-1: 展示企业登录入口

未登录企业账号的普通员工可以在轻量企业入口或相关设置入口看到企业登录操作。实现 UJ-1。

**Consequences (testable):**
- 未存在有效企业登录态时，界面展示企业登录 CTA。
- 首次未登录且检测到企业配置时，聊天主界面空状态展示企业登录主入口；设置页保留企业登录次入口。
- 企业登录 CTA 不要求员工输入 API Key、Base URL 或手动选择模型供应商。
- 非企业配置场景下，现有 Cherry Studio 个人使用路径不被破坏。[ASSUMPTION: P0 可通过构建配置、运行时配置或上游配置判断是否展示企业入口。]

#### FR-2: 发起企业 OAuth 授权

员工点击企业登录后，Cherry Studio 可以打开企业 AI Infrastructure 提供的授权页，并带上客户端完成回调所需的安全参数。实现 UJ-1。

**Consequences (testable):**
- 授权页由企业 AI Infrastructure 承载，Cherry Studio 不实现授权页。
- Cherry Studio 使用可防 CSRF 的授权状态参数。
- 员工取消授权、授权失败或回调参数缺失时，Cherry Studio 保持未登录状态并提示可重试。
- 进入架构方案前，企业 AI Infrastructure 与 Cherry Studio 必须冻结最小 OAuth 契约：授权 URL、回调 scheme、必需回调参数、state 校验规则、token 交换、刷新、撤销和错误返回。

#### FR-3: 保存企业登录态

授权成功后，Cherry Studio 可以保存企业登录态，并让后续模型、知识库和技能请求使用该登录态。实现 UJ-1、UJ-4。

**Consequences (testable):**
- 登录成功后，应用可以判断当前账号已企业登录。
- 登录成功回到 Cherry Studio 后，界面展示企业名称、账号标识和默认模型名；如果默认模型可用，聊天输入框处于可直接输入状态。
- 登录态保存位置符合现有客户端安全和数据分层约束。
- Cherry Studio 不保存企业资源治理配置，只保存客户端使用所需的凭据、刷新材料或会话状态。
- P0 同一时间只保留一个活跃企业账号；登录另一个企业账号前必须清理上一企业账号的登录态、远端资源元数据缓存和企业偏好。

#### FR-4: 处理登录态刷新、过期和登出

Cherry Studio 可以在企业登录态过期时尝试刷新；刷新失败、上游撤销或员工主动登出时，清理本地企业登录态并提示重新登录。实现 UJ-4。

**Consequences (testable):**
- 企业接口返回未授权时，系统不会无限重试。
- 刷新失败后，模型、知识库和技能入口进入需要重新登录的状态。
- 员工登出后，本地企业登录态不可继续用于调用上游资源。
- 登录态失效后触发重新登录时，Cherry Studio 不清空员工当前未提交输入、已选远端知识库或技能参数；重新登录后若权限变化导致资源不可用，再显示资源不可继续的明确状态。

#### FR-5: 激活企业 Provider

登录成功后，Cherry Studio 可以把企业 Provider 设置为普通员工默认可用的模型入口。实现 UJ-1。

**Consequences (testable):**
- 登录成功后，聊天入口可使用企业 Provider 的默认模型。
- 普通员工不需要手动新增 Provider 或维护 API Key。
- 企业 Provider 与既有 Provider 系统的兼容边界由架构设计明确，PRD 不要求重写推理调用链。
- 员工可见界面不出现 Provider、Base URL、API Key 等内部配置概念；这些概念只可出现在架构、开发或诊断上下文中。

### 4.2 企业模型使用

**Description:** 员工登录后，Cherry Studio 从企业 AI Infrastructure 获取当前员工可用模型，并通过企业 Provider 使用这些模型。P0 重点是“默认可用”，不是模型市场、模型治理或高级参数配置。实现 UJ-1、UJ-4。

**Functional Requirements:**

#### FR-6: 获取当前账号可用模型

Cherry Studio 可以基于企业登录态获取当前员工可用的模型列表或默认模型信息。

**Consequences (testable):**
- 登录成功后，系统可以获取至少一个可用模型或明确展示“暂无可用模型”状态。
- 模型可见性由企业 AI Infrastructure 决定。
- Cherry Studio 不提供模型授权、模型上架或模型分组治理后台。
- 进入架构方案前，模型发现契约必须冻结模型标识、展示名称、可用状态、默认模型规则、禁用原因和错误分类映射。

#### FR-7: 使用默认企业模型发起对话

当上游提供默认模型时，员工可以不做模型选择直接发起对话。

**Consequences (testable):**
- 首次登录成功后，聊天输入可直接使用默认企业模型。
- 如果默认模型不可用，系统给出明确错误并允许员工从可用模型中选择其他模型。
- 对话中不暴露 API Key。
- 默认状态只突出推荐企业模型；存在多个企业模型时，可通过“其他企业模型”一类的展开入口选择，不要求员工理解 Provider 配置。

#### FR-8: 保留模型选择的最小能力

当上游给当前员工分配多个模型时，Cherry Studio 可以在现有模型选择体验中展示这些企业模型。

**Consequences (testable):**
- 员工只能选择上游返回且当前可见的企业模型。
- 不可用模型不会作为可调用模型继续展示，或会以禁用状态展示并说明原因。
- 选择企业模型不要求员工进入 Provider 配置页。

#### FR-9: 处理模型调用失败

模型调用因为登录态失效、权限变化、额度限制、模型下线或网络问题失败时，Cherry Studio 展示面向员工的可理解错误。

**Consequences (testable):**
- 401 / 403 类错误引导重新登录或说明权限不足。
- 429 / quota 类错误说明额度、频率或上游限制。
- 网络错误与上游业务错误在用户提示和日志中可区分。
- 模型不可用、权限不足、登录失效、额度限制、上游服务不可用和网络失败必须映射到稳定的用户提示类别和日志类别。

### 4.3 远端知识库消费

**Description:** P0 让员工看到并使用企业分配的远端知识库，但不把这些知识库深度复制为 Cherry Studio 本地主数据。Cherry Studio 通过现有知识库或对话相关入口承接远端知识库元数据和调用入口。实现 UJ-2、UJ-4。

**Functional Requirements:**

#### FR-10: 获取当前账号可见的远端知识库

Cherry Studio 可以基于企业登录态获取当前员工可见的远端知识库资源元数据。实现 UJ-2。

**Consequences (testable):**
- 登录成功后，系统可以拉取知识库列表。
- 知识库列表至少包含展示名称、资源标识、可用状态和必要描述。[ASSUMPTION: 上游会提供 P0 所需的知识库资源元数据契约。]
- 无可见知识库时，界面展示空状态，不提示员工手动导入企业知识库副本。
- 进入架构方案前，远端知识库必须选择并冻结一种 P0 调用形态：检索 API、问答 API，或作为聊天请求中的上下文资源引用。

#### FR-11: 在现有知识库体验中展示远端知识库

Cherry Studio 可以在现有知识库入口或对话知识选择入口中展示远端知识库，并清晰区分其为企业远端资源。

**Consequences (testable):**
- 远端知识库不会被误认为本地创建的知识库。
- 员工可以看到哪些知识库来自企业账号。
- 远端知识库在列表、选择器和对话引用中统一展示企业标识、企业名称或等价来源标识。
- 远端知识库不提供本地编辑、删除、重建索引等治理操作。

#### FR-12: 使用远端知识库回答问题

员工可以选择远端知识库并在对话或相关入口中发起知识检索 / 问答。

**Consequences (testable):**
- 查询请求使用企业登录态访问上游能力。
- 回答或检索结果可回到当前会话或知识入口。
- 基于远端知识库产生的回答或检索结果应标识来源知识库；权限撤销或资源下线后，历史答案可保留展示，但不得继续使用该资源发起新调用。
- 当知识库权限被撤销时，后续调用失败并刷新资源可见状态。

#### FR-13: 限制本地持久化范围

Cherry Studio 对远端知识库只保存必要的本地缓存、会话引用和用户偏好，不保存可作为主数据的企业知识内容。

**Consequences (testable):**
- 本地删除缓存不会影响企业 AI Infrastructure 中的知识库。
- 本地不存在“编辑远端知识库内容并同步回上游”的 P0 能力。
- 日志不记录完整知识库内容或敏感查询正文，除非已有安全审计策略明确允许。

### 4.4 远端技能消费

**Description:** P0 让员工发现并调用企业分配的远端技能。技能定义、权限、版本和可见性由企业 AI Infrastructure 管理；Cherry Studio 只负责展示、选择、参数输入、调用和结果呈现。P0 中的远端技能限定为远端可执行入口，不包含本地 Agent 编排、MCP 工具注册、工作流编排或技能市场能力。实现 UJ-3、UJ-4。

**Functional Requirements:**

#### FR-14: 获取当前账号可见的远端技能

Cherry Studio 可以基于企业登录态获取当前员工可见的远端技能资源元数据。实现 UJ-3。

**Consequences (testable):**
- 登录成功后，系统可以拉取技能列表。
- 技能列表至少包含展示名称、资源标识、描述、输入要求和可用状态。[ASSUMPTION: 上游会提供 P0 所需的技能资源元数据和执行契约。]
- 无可见技能时，界面展示空状态。
- 进入架构方案前，远端技能执行契约必须冻结元数据、输入 schema、调用接口、结果 schema、同步/异步返回方式、超时和错误分类。

#### FR-15: 在现有技能体验中展示远端技能

Cherry Studio 可以在现有技能入口或对话可用技能入口中展示远端技能，并清晰区分其为企业远端资源。

**Consequences (testable):**
- 远端技能不会被误认为本地安装技能。
- 远端技能在列表、选择器和执行结果中统一展示企业标识、企业名称或等价来源标识。
- 员工不能在 P0 中编辑、发布或删除远端技能。
- 技能被上游撤销后，本地入口会消失或禁用。

#### FR-16: 调用远端技能

员工可以选择远端技能，输入必要参数，并由 Cherry Studio 调用企业 AI Infrastructure 执行技能。

**Consequences (testable):**
- 技能调用使用企业登录态。
- 执行结果能呈现在当前任务上下文中。
- 参数缺失、权限不足、执行失败和上游超时有明确错误状态。

#### FR-17: 处理技能版本和可用性变化

Cherry Studio 可以处理远端技能版本变化、下线或权限变化，不依赖本地固定副本继续执行。

**Consequences (testable):**
- 本地缓存过期后会重新确认技能元数据。
- 上游返回资源不存在或不可用时，入口被刷新或禁用。
- 历史会话中引用过的远端技能不保证可再次执行。

### 4.5 轻量企业入口

**Description:** P0 不重做完整首页，也不实现首页 Agent。轻量企业入口只承担企业登录、登录状态、默认模型、企业知识库和企业技能可达性的最小发现职责。实现 UJ-1、UJ-2、UJ-3。

**Functional Requirements:**

#### FR-18: 展示企业账号状态

员工可以看到当前是否已企业登录，以及当前企业账号的基础身份信息。

**Consequences (testable):**
- 已登录状态至少展示账号名、邮箱或上游返回的可展示身份之一。
- 已登录状态同时展示企业名称或等价企业标识，以及当前默认模型名；默认模型可用时，员工可以直接从聊天输入继续。
- 未登录状态展示登录入口。
- 身份信息缺失时，仍能显示“已登录企业账号”的稳定状态。

#### FR-19: 暴露三类 P0 能力入口

轻量企业入口可以把模型、知识库和技能三类企业能力引导到现有体验中。

**Consequences (testable):**
- 员工可以从轻量入口到达聊天 / 模型使用路径。
- 员工可以从轻量入口到达企业知识库相关路径。
- 员工可以从轻量入口到达企业技能相关路径。
- 三类入口必须保持统一企业资源标识，避免员工混淆本地资源和远端企业资源。

#### FR-20: 不实现首页 Agent

P0 的轻量企业入口不根据身份动态生成完整首页、不做个性化推荐、不以 Agent 方式主动编排首页内容。

**Consequences (testable):**
- 首页 Agent、岗位能力卡片、首登主动引导 AI 不进入 P0 验收。
- 轻量入口的 P0 主入口是聊天主界面的未登录空状态；设置页提供次入口；具体视觉样式由 UX 后续确定。
- P0 不要求重排 Cherry Studio 全局导航。

### 4.6 客户端纯边界与本地状态

**Description:** 本项目必须保持 Cherry Studio 的客户端边界。所有资源治理、权限配置、员工分组、OAuth 授权页和服务端策略都由企业 AI Infrastructure 完成。Cherry Studio 只保存客户端运行必需的状态。实现 UJ-1 至 UJ-4。

**Functional Requirements:**

#### FR-21: 不提供企业管理后台

Cherry Studio P0 不提供企业资源管理、权限管理、员工管理、岗位包管理或审计配置界面。

**Consequences (testable):**
- 产品中不存在用于配置企业知识库可见性、技能可见性或模型权限的管理入口。
- 管理员需求被记录为上游企业 AI Infrastructure 范围。
- Cherry Studio 只展示当前员工已被上游授权可见的结果。

#### FR-22: 不实现服务端策略逻辑

Cherry Studio 不在本地判断企业资源最终权限，不承担服务端策略执行。

**Consequences (testable):**
- 本地筛选只用于展示和体验，不作为安全边界。
- 上游拒绝访问时，Cherry Studio 不能用本地缓存绕过。
- 权限、额度、资源上下线最终由企业 AI Infrastructure 返回结果决定。

#### FR-23: 控制本地缓存和偏好范围

Cherry Studio 只保存客户端体验所需的缓存、偏好和会话引用。

**Consequences (testable):**
- 缓存可被清理，并能从上游重新拉取资源元数据。
- 本地偏好不改变上游资源权限。
- 敏感 token 和资源元数据的存储位置、生命周期和清理行为在架构设计中明确。

### 4.7 通用状态、缓存与恢复规则

**Description:** 模型、远端知识库和远端技能共享一套状态表达和恢复规则，避免员工在资源为空、权限失败、资源撤销或登录失效时看到互不一致的体验。实现 UJ-1 至 UJ-4。

**Functional Requirements:**

#### FR-24: 统一资源状态矩阵

Cherry Studio 必须用一致的方式表达企业模型、远端知识库和远端技能的可用性状态。

**Consequences (testable):**
- 企业资源状态至少覆盖：可用、暂无授权资源、加载失败、无权限、登录失效、资源已撤销、资源已下线、调用超时、缓存过期 / 离线展示。
- 每类状态都有明确下一步：重新登录、刷新资源、返回选择、重试、联系企业 IT / AI 平台团队，或复制错误信息。
- 空状态必须区分“当前账号暂无授权资源”“资源加载失败”“企业未配置该类资源”，不得只用一个泛化空状态承接全部失败。

#### FR-25: 缓存只加速展示，不授权执行

Cherry Studio 可以缓存远端资源元数据改善体验，但缓存不能成为资源权限或可执行性的依据。

**Consequences (testable):**
- 本地缓存可以用于展示最近一次远端资源元数据，但必须标识 fresh、stale、offline 或 revoked 等状态。
- 任何实际模型、知识库或技能调用都必须使用有效企业登录态并以企业 AI Infrastructure 返回结果为准。
- 上游返回 401 / 403 / 资源不存在 / 资源已撤销后，本地缓存不得继续让该资源作为可调用资源使用。
- 强制刷新或缓存损坏时，系统可以清理企业资源元数据并从上游重新拉取。

#### FR-26: 登录失效恢复保护当前任务

企业登录态失效或需要重新登录时，Cherry Studio 应尽量保护员工正在进行的任务上下文。

**Consequences (testable):**
- 重新登录流程不清空当前会话输入草稿、已选择的远端知识库或未提交的技能参数。
- 重新登录成功后，系统恢复当前会话和已选资源；若资源权限变化导致不可继续，显示“资源已不可用”并允许员工重新选择。
- P0 只支持单个活跃企业账号；切换企业账号时，必须明确提示并清理上一账号的登录态、企业资源元数据缓存和企业偏好。

## 5. Non-Goals (Explicit)

- 不做企业 AI Infrastructure 服务端。
- 不做 OAuth 授权页、授权服务器、用户目录或企业 SSO 服务端集成。
- 不做企业管理员后台。
- 不做资源治理、权限配置、员工分组、岗位能力包配置。
- 不做助手、工作流、MCP 工具的企业远端资源接入。
- 不做完整混合型首页、首页 Agent、首登主动引导 AI。
- 不做专业模式。
- 不做多企业账号同时在线或多租户切换体验；P0 只支持单个活跃企业账号。
- 不做远端知识库或远端技能的本地主数据复制。
- 不重写模型推理调用链，除非架构验证现有调用链无法承接企业 Provider。
- 不要求普通员工理解或维护 API Key、Base URL、Provider 高级参数。

## 6. MVP Scope

### 6.1 In Scope

- 企业登录入口。
- 与企业 AI Infrastructure OAuth 授权页的客户端发起和回调处理。
- 企业登录态保存、刷新、登出和失效处理。
- 企业 Provider 激活为普通员工默认模型入口。
- 当前员工可见模型获取和默认模型对话。
- 当前员工可见远端知识库获取、展示和调用。
- 当前员工可见远端技能获取、展示和调用。
- 轻量企业入口，用于展示企业账号状态并引导到模型、知识库和技能三类能力。
- 明确空状态、权限不足、登录失效、网络失败和资源不可用错误。
- 统一企业资源状态矩阵、缓存与撤销规则、登录失效后的任务恢复规则。
- 单个活跃企业账号策略，以及切换账号时的企业登录态、资源元数据缓存和企业偏好清理。
- 仅保存必要本地状态、缓存、偏好和会话引用。

### 6.2 Out of Scope for MVP

- 企业管理员配置台：由企业 AI Infrastructure 负责。
- 岗位能力包：后续在上游资源分配和客户端编排能力稳定后再扩展。
- 助手、工作流、MCP 工具企业远端接入：P0 先只做模型、知识库、技能。
- 专业模式：后续支持高级用户和更自由配置。
- 首页 Agent：P0 先做轻量入口。
- 资源版本治理、审批、审计报表：由上游系统承担。
- 离线使用企业远端资源：P0 不保证离线可用。
- 多企业账号同时在线、企业账号快速切换和跨企业资源并存。

## 7. Cross-Cutting NFRs

### 7.1 Security

- OAuth 回调必须防止伪造 state 和错误窗口接收结果。
- token 和刷新材料不得暴露给渲染层非必要代码路径。
- 日志不得输出完整 token、API Key、授权码或敏感响应体。
- 本地缓存不能作为权限绕过依据。
- 登出和授权失效后，不得继续使用旧凭据调用上游。
- OAuth 最小契约冻结前不得进入实现拆解，至少包括授权 URL、回调 scheme、state 校验、token 交换、刷新、撤销和错误返回。

### 7.2 Privacy and Data Governance

- 企业资源主数据归企业 AI Infrastructure 所有。
- Cherry Studio 不本地持久化企业知识库内容作为主数据。
- 查询内容、技能参数和响应内容的日志策略必须遵循现有日志规范，并默认避免记录敏感正文。
- 员工身份信息只展示和保存 P0 体验所需的最小字段。

### 7.3 Reliability

- 网络失败、上游 5xx、登录态失效和资源不可用必须有可恢复路径。
- 资源列表拉取失败不应导致应用整体不可用。
- 资源缓存过期或损坏时，系统应能清理并重新拉取。
- 已有个人版路径在非企业场景下不应被破坏。
- 资源元数据缓存必须区分 fresh、stale、offline 和 revoked 等状态；stale / offline 缓存只能用于展示，不能用于绕过上游权限执行。

### 7.4 Performance

- 企业登录成功后的首轮资源拉取不应明显阻塞主界面可交互状态。
- 资源列表应支持合理缓存，避免每次进入入口都全量请求上游。
- 模型、知识库和技能调用的性能预算由上游能力共同决定；Cherry Studio 侧不得引入明显额外串行等待。
- 性能阈值由架构和测试阶段冻结，至少覆盖登录到模型列表 p95、首次对话 p95、资源发现 p95、技能执行超时上限和客户端重试次数上限。

### 7.5 Observability

- 企业登录、资源拉取、模型调用、知识库调用、技能调用的失败原因应有可诊断日志。
- 日志上下文必须能区分模型、知识库、技能三类资源失败。
- 用户提示不暴露敏感内部信息；开发日志保留足够错误上下文但脱敏。
- 埋点事件模型需覆盖企业登录、首次对话、资源发现空状态、知识库调用、技能执行和手动 Provider 配置触碰，用于支撑成功指标采集。

### 7.6 Accessibility and i18n

- 新增用户可见文本必须走现有 i18n 体系。
- 登录、空状态、错误状态和入口按钮必须可键盘访问。
- 轻量企业入口应符合现有 Cherry Studio 设计系统和可访问性基线。
- 企业登录入口、资源选择、错误状态和重新登录恢复路径必须具备键盘可达验收。

## 8. Integration and Dependencies

- 企业 AI Infrastructure 必须提供 OAuth 授权页、token 交换 / 刷新 / 撤销能力。
- 企业 AI Infrastructure 必须提供当前员工可用模型的发现能力，包括模型标识、展示名称、可用状态、默认模型规则、禁用原因和错误分类。
- 企业 AI Infrastructure 必须提供当前员工可见知识库的元数据与调用能力，并在进入架构方案前确认 P0 使用检索 API、问答 API，还是聊天上下文引用。
- 企业 AI Infrastructure 必须提供当前员工可见技能的元数据与执行能力，包括输入 schema、调用接口、结果 schema、同步/异步模式、超时和错误分类。
- Cherry Studio 架构需确认企业 Provider 与现有 Provider / AI Core / provider registry / CherryIN OAuth 样板的复用关系，并明确它是独立 provider type 还是现有调用形态上的 credential resolver。
- UX 需围绕聊天主界面未登录空状态和设置页次入口设计轻量企业入口。
- 安全设计需确认 token 存储、刷新、登出清理和渲染层暴露边界。

## 9. Constraints and Guardrails

- Cherry Studio 是纯客户端，不引入企业服务端职责。
- 上游是企业资源和权限的 source of truth。
- P0 以普通员工通用场景为主，不做岗位定制。
- P0 只接模型、知识库、技能。
- P0 中远端技能只表示远端可执行入口，不承诺 Agent 编排、MCP 工具注册、工作流编排或技能市场能力。
- P0 同一时间只支持一个活跃企业账号。
- 优先复用现有容器和调用路径，避免重做产品结构。
- 如果现有结构无法承接远端资源，架构文档需明确最小必要改造，不在 PRD 中扩大范围。

## 10. Rollout and Change Management

- **Phase 0: 契约确认。** 与企业 AI Infrastructure 冻结 OAuth、模型发现 / 默认模型、知识库调用、技能执行、资源缓存 / 撤销五类契约。
- **Phase 1: 登录 + 企业 Provider。** 跑通授权、登录态、企业 Provider 默认模型对话。
- **Phase 2: 远端知识库。** 在现有知识库 / 对话入口中展示和调用远端知识库。
- **Phase 3: 远端技能。** 在现有技能 / 对话入口中展示和调用远端技能。
- **Phase 4: 轻量入口 polish。** 汇总登录状态、模型、知识库、技能的发现入口，处理空状态、权限失败、登录失效和资源撤销状态。
- **Phase 5: 内部试点。** 选择小范围普通员工验证登录即用、资源可见性和错误恢复。

## 11. Risks and Mitigations

- **R-1: 上游契约不稳定导致客户端反复返工。** Mitigation: Phase 0 先冻结 P0 OAuth、资源元数据和调用契约。
- **R-2: 远端资源嵌入现有容器时语义混淆。** Mitigation: UI 明确标识企业远端资源，并禁用本地治理动作。
- **R-3: 登录成功但资源为空造成员工误解。** Mitigation: 空状态明确说明“当前企业账号暂无可用资源”，并提示联系企业管理员或等待上游配置。
- **R-4: 客户端缓存被误当权限依据。** Mitigation: 所有实际调用以企业 AI Infrastructure 返回为准；本地缓存只改善展示体验，且必须区分 fresh、stale、offline 和 revoked 状态。
- **R-5: P0 被拉大成企业工作台重构。** Mitigation: 首页 Agent、岗位能力包、专业模式、管理员后台全部明确出 P0。
- **R-6: token 泄漏或日志误打敏感信息。** Mitigation: 安全设计和日志检查作为实现验收项。
- **R-7: 多企业账号引入资源隔离和缓存命名复杂度。** Mitigation: P0 明确只支持单个活跃企业账号，切换账号时清理上一账号登录态、资源元数据缓存和企业偏好。

## 12. Success Metrics

**Primary**

- **SM-1: 登录到首次成功对话完成率** — 内部试点员工中，从未登录状态开始，成功企业登录并完成一次默认模型对话的比例达到 90% 以上。验证 FR-1 至 FR-9。
- **SM-2: 零手动配置使用率** — 内部试点员工中，无需手动输入 API Key / Base URL / Provider 配置即可使用企业模型的比例达到 95% 以上。验证 FR-1、FR-5、FR-7。
- **SM-3: 远端资源可用闭环** — 已分配知识库和技能的试点账号中，至少 90% 可以在 Cherry Studio 中看到并成功调用对应资源。验证 FR-10 至 FR-17。

**Secondary**

- **SM-4: 授权失败可恢复率** — 模拟取消授权、过期 token、上游 401 后，员工可以重新登录并恢复模型使用。验证 FR-2、FR-4、FR-9。
- **SM-5: 资源空状态识别率** — 无资源账号看到明确空状态，不误以为本地导入或手动配置是必需路径。验证 FR-10、FR-14、FR-19。
- **SM-6: 试点 7 日继续使用率** — 内部试点员工完成首次企业登录和首次对话后，7 日内再次使用企业模型、远端知识库或远端技能的比例。用于验证 P0 不只是接入成功。
- **SM-7: 首次可用答案耗时** — 从员工打开 Cherry Studio 到获得第一次可用企业模型回答的中位耗时。用于衡量登录、默认模型和首轮对话体验。
- **SM-8: 任务完成自评** — 试点员工在使用企业模型、远端知识库或远端技能完成一次任务后，对“是否完成当前任务”的轻量自评结果。

**Counter-metrics (do not optimize)**

- **SM-C1: 本地资源复制量** — 不应为了提升“资源可见数量”而把企业知识库或技能深度复制为本地主数据。反向约束 FR-13、FR-17、FR-22。
- **SM-C2: UI 入口数量** — 不应通过增加大量入口来提升发现率。P0 应保持轻量入口，不重做首页。反向约束 FR-18 至 FR-20。
- **SM-C3: 客户端策略判断数量** — 不应把权限策略下沉到 Cherry Studio 本地以减少上游调用。反向约束 FR-21、FR-22。

**Required ATDD Scenarios**

- **ATDD-1: 首次企业登录并完成默认模型对话。** 从未登录状态开始，员工点击企业登录，完成授权回调，返回 Cherry Studio 后看到企业账号、默认模型，并在不输入 API Key / Base URL / Provider 配置的情况下完成一次对话。
- **ATDD-2: 已分配远端知识库成功调用。** 已企业登录且上游分配知识库的员工，在企业知识库入口或对话知识选择入口看到企业知识库标识，选择知识库发起问题，得到带来源标识的回答或检索结果。
- **ATDD-3: 已分配远端技能成功执行。** 已企业登录且上游分配技能的员工，在技能入口或对话技能入口看到企业技能标识，按输入 schema 填写参数，执行技能并在当前任务上下文看到结果。

## 13. Open Questions

### 13.1 架构前置阻塞项

这些问题不阻塞 PRD 定义，但会阻塞架构方案和开发任务拆解。进入架构方案前必须由 Cherry Studio 架构侧与企业 AI Infrastructure 项目共同确认。

1. OAuth 契约是否沿用现有 CherryIN OAuth 形态，还是新增企业专用端点？最小契约需包含授权 URL、回调 scheme、必需参数、state 校验、token 交换、刷新、撤销和错误返回。
2. 企业 Provider 是独立 provider type，还是现有调用形态上的 credential resolver？模型资源发现接口返回的字段、默认模型规则和错误分类是什么？
3. 远端知识库的调用方式是检索 API、问答 API，还是作为聊天请求中的上下文资源引用？
4. 远端技能的执行契约是什么：元数据、输入 schema、调用接口、结果 schema、同步 / 异步模式、超时和错误分类分别是什么？
5. 资源元数据缓存 TTL、强制刷新、stale / offline 展示和上游撤销后的客户端刷新策略是什么？

### 13.2 UX 前置阻塞项

这些问题不阻塞架构骨架，但会阻塞可交付 UX 方案和验收文案。

1. 企业资源状态矩阵的最终文案和动作是什么：暂无授权资源、加载失败、无权限、登录失效、资源已撤销、资源已下线、调用超时、缓存过期 / 离线展示。
2. 企业模型、远端知识库和远端技能的统一企业标识使用什么视觉形式：企业标签、企业名称、远端资源图标，或组合方案。
3. 登录成功确认态如何呈现企业名称、账号标识和默认模型名，同时保持员工可以立即开始输入。

### 13.3 非阻塞产品细化项

这些问题可以在架构并行推进时由产品、UX 或试点负责人补齐。

1. 企业 Provider 的产品命名和 provider id 是什么？
2. 内部试点的账号、资源样本和成功指标采集方式由谁负责？
